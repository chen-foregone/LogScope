# LogScope 首版实施规格

Status: ready-for-agent
日期：2026-11-02

2026-11-04 产品决策修订：首版取消延期功能；保留到期前7天提醒及到期后待确认清理，不操作不删除，也不自动续期。本修订取代此前延期要求。

此状态表示规格完整、可交接给代理用于实施规划，不表示所有真实集成工作均已满足直接开工条件。产品规则以 README 已批准规则为依据，术语遵循 GLOSSARY；用户已明确同意本规格所述测试边界。技术设计与集成选择的授权层次见第四段与第七段。先前提出的 18 张工单仅为未获批准的草案，本规格不沿用其作为已确认拆分，本次不创建或落盘工单，不实现代码。

## Problem Statement

LogScope 需要将只读日志故障排查原型变为可持久保存、可追溯、可取消并可逐轮重新调查的首版闭环。当前只有 Vue 单组件内存样例，搜索与服务筛选生效，新建记录错误地默认低严重程度并进入调查中；时间筛选与大部分概况仍是展示。FastAPI 只有根响应与常量健康响应，数据库仅有 SQLAlchemy 连接及基类；没有业务模型、迁移、测试、真实日志连接器、Agent、执行器或时钟适配器。依赖声明包含 Alembic 并不意味着已有迁移。

核心问题不是补几个界面字段，而是同时保证：调查只读、证据经脱敏且能核验、结论不越过证据、历史不被新轮覆盖，以及取消、失联、重启和并发时不会产生两轮同时执行或旧执行污染新轮。已完成不等于确认根因，保存成功也不等于运行任务可以自动续跑。

## Solution

在现有 Vue、FastAPI、PostgreSQL 骨架上逐步补全调查工作台、业务操作契约、持久化领域模型、受控执行边界、日志与 Agent 适配器。形成“创建待处理记录—固定范围启动—只读收集并脱敏—保存证据与分析—明确结束—用户按需新轮”的闭环。

业务记录、历史和统计以服务端持久化事实为准。执行与外部来源允许通过适配点测试，但首版交付必须接通选定的真实日志来源与 Agent，并验证只读权限和旧执行隔离。界面只呈现真实业务状态、证据条数和概况，不以样例常量代替已实现能力。

## User Stories

以下 US-01 至 US-48 为连续编号的可验收用户故事；详细规则集中在第四段，验收绑定见第五段。

- **US-01**：作为排查用户，我希望先创建待处理且严重程度未评估的调查记录，以便在条件未齐备时登记问题而不误启动。
- **US-02**：作为排查用户，我希望启动前确定服务并调整默认最近 1 小时、最长 24 小时的日志范围，以便针对明确对象排查。
- **US-03**：作为排查用户，我希望启动后服务与起止时间固定，以便本轮调查范围不会随时间或编辑悄然变化。
- **US-04**：作为排查用户，我希望所有调查仅只读访问被调查环境且修复建议不被自动执行，以便保护环境。
- **US-05**：作为排查用户，我希望列表整体状态跟随最新一轮且可查看每轮独立历史，以便理解当前进展与此前结果。
- **US-06**：作为排查用户，我希望排查正常结束但证据不足时显示已完成和未确定根因，以便区分排查结束与根因确认。
- **US-07**：作为排查用户，我希望技术故障无法继续时显示失败及原因，以便不将未找到根因误当技术失败。
- **US-08**：作为排查用户，我希望临时查询故障按明确超时与有限重试处理，以便避免无限等待和无意义请求。
- **US-09**：作为排查用户，我希望单轮包含重试的总时限受控，以便排查不会无限运行。
- **US-10**：作为排查用户，我希望部分来源不可用时在仍可排查的前提下继续并标明缺失，以便不将查不到误解为没有异常。
- **US-11**：作为排查用户，我希望取消后立即停止安排新操作并尽力中止在途请求，以便主动停止排查。
- **US-12**：作为排查用户，我希望停止未确认时仍显示调查中及正在停止，确认终止后才为已取消，以便不提前启动替代轮次。
- **US-13**：作为排查用户，我希望保留停止前已保存证据而排除停止后迟到结果，以便取消不会丢失既有产物或混入新产物。
- **US-14**：作为排查用户，我希望失败、已取消或已完成后均能在原调查手动发起新轮且无累计次数上限，以便继续调查而不覆盖历史。
- **US-15**：作为排查用户，我希望每轮分别保存服务与范围并且新轮不自动视为继承了上一轮的证据覆盖，以便调整范围后仍能准确判断覆盖情况。
- **US-16**：作为排查用户，我希望重复或并发启动同一调查至多产生一个运行轮次，以便避免重复执行。
- **US-17**：作为排查用户，我希望实例最多运行三个调查且满额直接提示稍后重试而不排队，以便准确理解是否已启动。
- **US-18**：作为排查用户，我希望执行失联时先确认旧执行不能运行或写入再结束旧轮，以便不产生重叠执行。
- **US-19**：作为排查用户，我希望刷新或页面断连不改变运行状态且服务重启不自动续跑，以便区分页面连接、持久记录与执行生命周期。
- **US-20**：作为证据使用者，我希望每条支撑结论的证据包含来源、发生时间、查询条件和可核验片段或稳定定位，以便追溯依据。
- **US-21**：作为证据使用者，我希望敏感内容在保存、展示和交给 Agent 前脱敏且不可靠脱敏的内容被排除并提示，以便避免信息泄露。
- **US-22**：作为证据使用者，我希望同调查跨轮身份代号一致而不同调查独立，凭据直接屏蔽且不保存原敏感值，以便兼顾关联分析和隐私。
- **US-23**：作为证据使用者，我希望同轮仅对可靠判定为同一原始记录的证据去重，以便不重复计数也不误合并不同日志。
- **US-24**：作为证据使用者，我希望无法可靠判同时保留证据并提示可能重复，以便不因相同文本或摘要丢失记录。
- **US-25**：作为排查用户，我希望历史证据经本轮范围与可核验性检查后才能引用且标明来源轮次，以便不把历史自动当作当前证据。
- **US-26**：作为排查用户，我希望本轮纳入的同一证据只计一次、历史独存证据不计本轮，以便证据条数反映最新轮事实。
- **US-27**：作为证据使用者，我希望来源不可访问时按已保留核验材料区分可核验与不可核验，以便不一概丢弃仍可核验依据。
- **US-28**：作为结论阅读者，我希望确认根因必须说明因果链、关键矛盾及替代解释，以便不把数量或时间相关当作因果证明。
- **US-29**：作为结论阅读者，我希望证据不足时只呈现带依据与缺口的待验证假设，以便明确结论边界。
- **US-30**：作为结论阅读者，我希望关键证据失效且缺乏其他充分支撑时结论变为待重新核验并保留历史，以便不误认为原结论已被推翻或调查已重开。
- **US-31**：作为排查用户，我希望通过手动新一轮只读核验且获得充分因果证据后才恢复确认，以便重新确认有据可查。
- **US-32**：作为排查用户，我希望严重程度按业务影响定性评估而非根因可信度或排查优先级，以便正确表达高、中、低和未评估。
- **US-33**：作为排查用户，我希望 Agent 评估及人工调整均记录依据、时间和历史，以便追踪等级变化。
- **US-34**：作为排查用户，我希望人工等级不被 Agent 覆盖、新建议经我确认后才应用，以便保持人工决策优先。
- **US-35**：作为排查用户，我希望新轮保留人工等级并展示评估时间和历史影响提示，以便不误认为该等级已验证当前影响。
- **US-36**：作为排查用户，我希望刷新和服务重启后仍可查看调查、逐轮脱敏证据、结论与变更历史，以便调查产物持久可追溯。
- **US-37**：作为列表用户，我希望创建、启动、状态、证据、结论和等级变化更新最后更新时间，而查看与检索不更新，以便列表反映真实业务变化。
- **US-38**：作为列表用户，我希望搜索、服务筛选及最后更新时间筛选共同作用，以便找到相关调查并区分日志范围。
- **US-39**：作为列表用户，我希望时间以 UTC+8 展示、统一基准保存且固定筛选左闭右开，以便边界一致。
- **US-40**：作为列表用户，我希望相对时间筛选在应用或刷新时固定，列表与概况共用边界且翻页不变，以便跨页统计可比。
- **US-41**：作为列表用户，我希望概况按全部匹配调查展示总数、活跃数、待处理数和最新轮证据总数，以便统计不受当前页影响。
- **US-42**：作为列表用户，我希望证据条数不代表日志扫描数、故障数或根因数，且不展示虚构告警或完整率，以便不被样例指标误导。
- **US-43**：作为记录保管者，我希望默认按最近一轮结束后 30 天保留、无轮从创建起算且新轮重算运行中不清理，以便期限与调查生命周期一致。
- **US-44**：作为记录保管者，我希望仅查看不延长保留期，到期前 7 天得到到期提醒，以便安排材料保管；到期后不确认清理就继续保留，但不自动续期。
- **US-45**：作为记录保管者，我希望到期后先标记待确认、明确范围和不可恢复性后由我确认清理，以便不被静默永久删除。
- **US-46**：作为记录保管者，我希望清理只影响指定调查产物、不删除源日志或误删其他调查引用，以便保持只读边界与引用安全。
- **US-47**：作为系统维护者，我希望受控执行写入识别所属调查、轮次和执行身份并隔离旧执行，以便竞争、取消和重启下状态与数据保持一致。
- **US-48**：作为交付验收者，我希望用真实业务 API、PostgreSQL、真实迁移及选定日志连接器和 Agent 的集成验收首版，以便测试替身通过不被误认作真实集成完成。

## Implementation Decisions

### D1. 授权层次、领域关系与持久化

**已确认产品决策**：上述业务行为及历史保留规则已经批准；第五段主验收边界已经用户确认。现有骨架需补全，而不是把样例认定为已有业务能力。

**为实施提出的技术设计，非用户已批准的技术细节**：沿现有 Vue/FastAPI/PostgreSQL 分层补全；新增真实数据库迁移来创建和演进持久化业务结构。调查拥有多次调查尝试；每次尝试拥有不可变启动范围、执行阶段、结束原因和证据纳入关系。证据保存脱敏核验材料及来源身份；“证据记录”与“本轮纳入引用”分离，允许历史证据引用且不覆盖原轮归属。结论版本关联支撑证据及核验状态变化；严重程度变更独立记录人工或 Agent 来源、依据和评估时间；保留期限属于调查生命周期管理。

以事务保障启动、实例名额、状态变更、证据去重与纳入、人工等级确认、结论版本、清理之间的竞争一致性。历史用追加版本和关系表达，不以当前值更新覆盖过去；可维护当前视图但应可追溯。事务失败不留下貌似运行的新轮或半套引用；具体持久化结构、锁与隔离机制尚未选定，不在此指定表名、队列或执行框架。

### D2. 状态维度与轮次启动

**已确认产品决策**：

| 维度 | 含义与边界 |
| --- | --- |
| 调查整体状态 | 无轮次为待处理；有轮次跟随最新一轮状态，不汇总或改写旧轮。 |
| 轮次状态 | 调查中、已完成、失败、已取消；创建待处理记录不是创建运行轮次。 |
| 执行阶段 | 正在停止、正在确认执行状态均属于尚未结束的调查中，不是终态。其他进度名称是待设计展示，不另造业务状态。 |
| 调查结果 | 区分已确认根因与未确定根因；正常完成可未确定，失败与取消不冒充完成结果。待验证假设不因结束自动确认。 |
| 结论核验状态 | 待重新核验描述当前结论依据的有效性，不代表调查重开、轮次失败或原结论被推翻。 |
| 工单 Status | ready-for-agent 等仅为文档/分诊状态，与上述所有业务状态独立；本次没有工单。 |

启动必须确定服务与日志时间范围；默认最近 1 小时、跨度最多 24 小时，启动前可调整，启动时固化起止时间且不滑动。正在运行的轮次不得修改服务或范围，需先结束或取消后新轮。失败、已取消、已完成后均由用户手动在原调查启动新一轮，可调整服务与范围，无累计次数上限；不自动重开，不覆盖旧轮状态、失败原因、范围、证据或结论。单轮查询重试不是新一轮。

同调查至多一轮调查中，重复点击和并发请求原子保护。实例同时最多三个调查运行；满额拒绝并提示稍后重试，不后台排队，也不生成貌似已运行的新轮。

### D3. 只读执行、查询韧性与退出安全

**已确认产品决策**：真实日志连接器和 Agent 工具均限定对被调查环境只读，不重启服务、不改配置、不删除日志；用户要求修复也不改变此边界。允许写入独立的调查产物存储，修复建议仅供参考。

单次原始日志查询超时 30 秒；临时网络故障或超时最多额外两次重试，间隔依次 2 秒、5 秒。权限、凭据、参数错误不盲目重试；限流遵循来源要求，不绕过限制。单轮总时限 10 分钟包含重试及等待。必要查询持续失败以致无法继续，或达到总时限时记失败；有其他来源仍可支持排查则继续，标出缺失来源及覆盖不完整，不能将查不到当作没有异常或据此排除原因。正常结束证据不足为已完成／未确定根因。

取消立即停止安排新操作并尽力中止在途请求；正在停止期间仍调查中、占用名额、不可新轮；确认执行终止后才已取消。保留停止前已保存证据，停止后迟到结果不纳入，包括旧执行后续证据、结论和等级产物。

执行失联先进入正在确认执行状态，仍调查中并占用名额；只有确认旧执行不能继续运行或写入，才将服务中断影响轮次记失败、保留证据并允许新轮，注明中断原因。服务重启不自动续跑；单纯刷新或页面断连不是执行失败，也不是结束证明。

**为实施提出的技术设计**：需要持久可识别的执行身份、可靠的旧执行停止确认及旧写入隔离，所有执行端写入按轮次和有效执行身份受控；不能仅凭本地进程变量、页面断连或超时猜测已终止。具体执行器、隔离与确认机制待选。在达到时限的处理上同样不能通过抢先释放名额绕过旧执行安全边界。取消、超时、正常完成、失联同时发生时的原子裁决和可见结果须专门实现验证；当前没有另获批准的“取消总优先”或“超时总优先”业务规则，不预设新优先级，若实现需要改变既定终态含义则须回到用户确认。

### D4. 脱敏、证据身份与引用

**已确认产品决策**：脱敏先于持久化、展示及交 Agent。密码、令牌、密钥、会话凭据直接屏蔽；姓名、电话、邮箱、证件等替换成调查内一致、不暴露原值的代号。同调查各轮一致、不同调查独立。尽量保留错误码、时间和调用关联线索，含敏感信息的关联标识仍须处理；无法可靠脱敏的内容不纳入分析并提示不可用。保存脱敏片段、来源定位、查询条件及脱敏说明，不额外保存原敏感值。

支撑结论的每条证据至少有来源、日志发生时间、查询条件、可核验原文片段或稳定定位；这里原文片段仍须满足前置脱敏，不授权保留敏感原文。仅摘要且无法追溯原始日志不足以确认根因。

同轮同一来源的同一原始日志仅保留一条证据并计一次。优先按来源标识和稳定记录 ID 判同；文件来源可用稳定文件身份与偏移。不得仅凭时间、文本、摘要或脱敏后相同内容判同。内容相同但时间或来源不同可能是不同记录；不能可靠判同时保留并提示可能重复。

历史证据不自动继承。纳入前检查本轮服务和日志时间范围及仍可核验性，标记来源轮次；同一证据在本轮只计一次，历史独存不计本轮，引用不改写历史且不表示本轮覆盖完整。服务调整后尤其不能把上一轮覆盖当作新范围覆盖。

**为实施提出的技术设计**：脱敏管道覆盖请求处理、错误记录和执行端产物，防止旁路持久化或输出；一致代号机制不得依赖保存原敏感值。证据身份和引用约束在持久化事务中执行，不只在 UI 去重。具体算法、敏感检测与来源身份能力须随所选集成验证，不能宣称已实现可靠脱敏。

### D5. 结论、核验变化与严重程度

**已确认产品决策**：确认根因需要可核验因果证据链，说明故障现象、原因如何导致现象、关联证据、关键矛盾与替代解释处理；日志数量或时间相关本身不够，不强制两条证据。证据不足可提出待验证假设，但须列依据和缺失证据；未确定根因不是没有故障。

来源不可访问时，已保存可核验片段及来源信息的证据继续保留并标注来源不可访问；只有失效链接且无法核验则标不可核验，不再作为确认根因的充分依据。关键证据不可核验且无其他充分支撑时，当前结论为待重新核验，保留原结论与变更历史，不证明原结论错误，不改已结束轮次，也不自动新轮。通过手动新轮只读核验，有充分可核验因果证据后才恢复确认并留历史，不执行修复验证。

严重程度只衡量业务影响，不是优先级或根因可信度：高为核心业务不可用或大范围用户无法完成关键操作；中为部分业务受损或明显变慢但有替代路径完成关键操作；低为局部轻微且不妨碍关键业务；影响信息不足为未评估，不等于低风险。首版不设统一量化阈值，依据尽量注明业务、用户范围、持续情况和替代路径，原因不明不成为降低等级的理由。

Agent 可评估、用户可调整，每次均记依据、来源、时间和历史。人工调整后 Agent 只能提交新建议及依据，用户确认才应用；新轮不清空人工等级，展示评估时间并说明保留不等于验证当前影响。结论核验变化、轮次状态和严重程度独立表达。

### D6. 列表、更新时间与概况

**已确认产品决策**：创建调查、启动新轮、状态变化、新增证据、结论变化、严重程度调整更新最后更新时间；查看、搜索、筛选不更新。列表时间按此时间而非日志发生时间筛选；每轮日志范围单独展示。以北京时间 UTC+8 展示，保存统一时间基准，固定区间左闭右开。相对范围在应用筛选或刷新时计算，列表和概况同次使用相同边界，翻页不改变范围。

搜索、服务、更新时间筛选共同决定匹配集合 M；概况覆盖全部 M，不局限当前页。只展示以下四项：

| 指标 | 计算公式 |
| --- | --- |
| 调查总数 | M 中调查数量。 |
| 活跃调查数 | M 中整体状态为调查中的调查数量，每个调查一次，不累加历史轮；正在停止及正在确认执行状态仍在其中。 |
| 待处理调查数 | M 中整体状态为待处理的调查数量。 |
| 证据总条数 | 对 M 各调查最新轮的已保存、去重、已纳入证据条数求和；无轮贡献 0，不跨调查去重。 |

已完成、失败、已取消、待处理均不计活跃。列表统一用“证据条数”，不称事件数，不统计扫描日志总量、不累计历史轮，不代表故障或已确认根因数量。各历史轮分别保留自己的条数。不展示待处理告警和证据完整率，不使用演示常量冒充真实统计。

**为实施提出的契约设计**：可沿用现有对调查标题、服务、编号的去空白、不区分大小写包含搜索。多轮服务可变时，列表服务展示及服务筛选究竟采用哪个调查级字段或最新轮投影尚未批准为新业务规则，需在具体 schema 设计时明确，并保证列表、搜索、筛选与概况一致可验收，不得暗中混用历史服务与当前服务。建议以同一筛选描述及相对时间边界快照供列表、概况和翻页使用；不要求未经讨论的跨页数据库内容快照隔离。

### D7. 保留、到期提醒与确认清理

**已确认产品决策**：默认保留到最近一轮结束后 30 天；没有轮次的待处理记录从创建起计。新轮启动重新计算保留周期，运行中不清理，结束后按该轮结束时间计算；仅查看不延长。到期前 7 天显示到期提醒；首版不提供延期操作。到期后标记待用户确认清理，不静默永久删除；不确认就继续保留，期限不自动延后。清理前明确指定调查内记录、逐轮尝试、脱敏证据、引用、结论及变更历史的实际清理范围和不可恢复性。不得删除被调查环境原始日志，不得误删其他调查仍需的引用或材料。

**为实施提出的技术设计**：确认清理与启动竞争时以事务重新校验当前保留状态和运行情况，避免基于过时预览清理；清理与重试应保持一致可理解的结果。首版不实现延期输入、延期API、延期版本或延期历史；后续如需延期，应另行确认需求。共享材料的引用保护与清理范围需随持久化设计实现，不能因一处删除使另一调查证据静默失效。

## Testing Decisions

### T1. 已确认测试边界与拟新增设施

用户已确认主验收 seam：通过 HTTP 业务 API，使用真实 PostgreSQL，经过真实领域规则、持久化和事务逻辑验证外部可见行为。日志来源、Agent、时钟和调度作为可控外部适配点，用于确定性触发超时、失联、重试和竞态。测试不以内部函数调用次数、私有结构或特定框架实现为断言目标。

当前无已有测试先例或现成测试框架；业务 API、迁移与各类测试设施均拟新增，不宣称现存。工具和运行方式待选，不指定未经批准的测试栈。测试替身可证明流程和边界行为，不能证明模型真实推理质量或真实日志协议可用。

另需少量 UI E2E 验证主要用户路径，真实 PostgreSQL 迁移集成测试，以及选定真实日志连接器的协议、身份、超时、脱敏入口和只读契约测试。时钟或调度可控不意味着绕过业务 API 直接拼造已通过状态；预置场景仅用于安排外部环境和测试数据。
