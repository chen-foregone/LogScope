# LogScope

日志故障排查 Agent 原型。结论需要关联可核验的日志证据。领域术语见 `GLOSSARY.md`。

## 已确认的业务规则

本节规则均为已批准的首版产品规则，不代表软件功能已经完成。本次新增或细化的能力当前骨架尚未实现；下文保留既有实现差距说明。

### 首版只读边界

- 首版调查流程仅对被调查环境执行只读操作；即使用户要求修复，也不得修改该环境，包括重启服务、修改配置或删除日志。
- 允许保存调查记录、证据和修复建议；保存这些调查产物不等于修改被调查环境。
- 修复建议仅供参考，不由首版调查流程自动执行。

以上是产品约束，不代表当前骨架已实现调查产物持久化或操作权限控制。

### 证据不足时的结论表达

- 缺少足以支持因果判断的可核验日志证据时，不得将推测呈现为已确认根因。
- 允许提出待验证假设，但必须说明其现有依据和缺失证据。
- 例如，仅观察到大量超时日志、没有证据证明数据库异常时，不能直接断言数据库是根因。

- 确认根因必须有可核验的因果证据链，说明故障现象、原因如何导致现象、关联证据，以及关键矛盾和替代解释如何处理。
- 日志数量或时间相关本身不足以确认根因；不强制要求两条证据。证据不足时仍为“待验证假设”。

满足以下证据最低要求不等于已经证明因果关系。当前骨架尚未实现相关校验。

### 日志证据最低要求

- 每条用于支撑结论的日志证据至少包含：来源、日志发生时间、查询条件，以及可核验的原文片段或稳定定位。
- 只有摘要、无法追溯原始日志的内容，不作为确认根因的充分依据。

- 允许引用历史轮次的证据，但不自动继承为本轮证据；引用前须检查其是否符合本轮服务和日志时间范围，并且仍可核验。
- 引用时标注来源轮次；纳入本轮的证据在本轮计数一次，仅在历史保留的证据不计入本轮。
- 引用不改写历史，也不代表本轮范围已经完整覆盖。

以上为首版最低要求；保存期限见“调查数据持久保存”。当前骨架尚未实现历史证据引用与本轮纳入判断。

### 日志证据的敏感信息处理

- 首版在持久化、展示或交给 Agent 分析前完成脱敏；密码、令牌、密钥及会话凭据直接屏蔽，姓名、电话、邮箱、证件等个人身份信息替换为调查内一致的代号。
- 脱敏时尽量保留错误码、时间及调用关联线索；关联标识含敏感信息时也须处理，不以保留线索为由暴露敏感信息。
- 无法可靠脱敏的内容不纳入分析，并提示该内容不可用。
- 该规则作用于调查侧的证据处理，不授权修改或删除被调查环境中的原始日志。

- 同一调查内，同一身份信息使用一致且不暴露原值的代号替换，以保留同一对象在不同日志中的关联关系。
- 密码、令牌和密钥直接屏蔽，不以保留关联线索为由暴露其原值。

- 首版不同调查使用独立代号，不跨调查复用同一身份信息的代号；同一调查的各轮尝试间保持代号一致。

- 脱敏后的核验材料包括脱敏片段、来源定位、查询条件和脱敏说明，不额外保存原敏感值。

代号生成算法属于后续实现细节，不在本节指定，也不作为业务规则确认的阻塞项。当前骨架尚未实现脱敏、核验材料处理及调查内一致、调查间独立的代号替换。

### 原始日志清理或定位失效后的证据处理

- 若已保存可核验的原文片段及来源信息，保留该证据，并标注原始来源已不可访问。
- 若仅有失效链接且无法再核验，标记为“不可核验”，不能继续作为确认根因的充分依据。
- 原始来源不可访问不等于所有已保存证据均不可核验；应依据实际保留的核验材料区分处理。

当前骨架尚未实现来源失效标记和证据核验状态处理。

### 关键证据失效后的结论处理

- 关键证据变为不可核验，且没有其他充分证据支撑时，将当前结论标为“待重新核验”。
- 保留原结论及变更历史，不将“待重新核验”解释为原结论已被证明错误。
- “待重新核验”属于结论的核验状态，不等于新一轮调查已启动，也不直接改写已结束轮次的调查状态。

- “待重新核验”的结论通过新一轮调查核验；只有获得充分的可核验因果证据才恢复确认，并保留原结论及状态变更历史。
- 重新核验仍为只读排查，不执行修复验证。

当前骨架尚未实现结论重新核验、新轮核验、恢复确认及变更历史。

### 调查启动条件

- 允许先创建待处理记录；创建记录不等于正式启动调查。
- 只有确定被调查服务和日志时间范围后，才允许进入“调查中”；任一项缺失时，记录保持“待处理”。

- 日志时间范围默认最近 1 小时，单轮最大跨度 24 小时；启动前可调整。
- 启动时固定该轮的起止时间，不随时间滑动；启动后不得修改本轮服务或日志时间范围，需先结束或取消本轮，再启动新一轮。

以上是已确认的产品规则；当前前端新建记录直接进入“调查中”的行为尚未按此规则调整，范围默认值、跨度限制和启动后固定范围尚未实现。

### 调查完成与调查结果

- “已完成”表示本次排查已经结束，不代表已经成功定位根因。
- 排查结束但现有证据不足以确定原因时，允许标记“已完成”，同时明确调查结果为“未确定根因”。
- 调查状态与调查结果应分别表达；结束调查不会使待验证假设自动成为已确认根因。

当前骨架尚未实现上述完成与结果表达逻辑。

### 调查失败

- 增加独立的“失败”状态，表示技术故障使调查无法继续并因此中止，例如日志源持续不可用。
- “失败”与“已完成但未确定根因”不同：前者未完成排查，后者完成了排查但证据不足。
- 不得仅因调查未找到根因而将其标记为“失败”。

- 单次日志查询超时为 30 秒；临时网络故障或超时最多额外重试 2 次，间隔依次为 2 秒和 5 秒。
- 权限、凭据或参数错误不盲目重试；限流遵循来源要求，不绕过来源限制。
- 单轮总时限为 10 分钟，包含重试。必要查询持续失败、导致排查无法继续，或达到单轮总时限时，记为“失败”。
- 部分来源仍可支持排查时，不因其他来源故障直接失败；正常结束但证据不足时，记为“已完成”，结果为“未确定根因”。

失败后新一轮的发起方式见“失败后的重试”。当前骨架尚未实现“失败”状态、查询超时重试及单轮总时限控制。

### 用户主动取消

- 允许用户主动停止正在进行的调查；点击取消后立即不再安排新操作，并尽力中止在途请求。
- 停止过程中显示“正在停止”，此时该轮仍处于“调查中”，不可重开；确认执行终止后才记为独立的“已取消”状态。
- 取消后保留停止前已保存的证据，停止后迟到的结果不再纳入；不将主动取消记为“失败”或“已完成”。
- 调查整体状态仍遵循最新一轮尝试的状态，取消不改写先前各轮历史。

- 取消后允许在原调查下发起新一轮尝试；已取消的那一轮保持“已取消”，其证据和历史记录不被覆盖。
- 新一轮仍遵循已确认的调查启动条件、同一调查的并发限制及整体状态展示规则。

不得将“正在停止”直接视为该轮已结束。当前骨架尚未实现取消、在途请求停止、迟到结果排除、“正在停止”展示、“已取消”状态及取消后发起新一轮尝试的逻辑。

### 失败后的重试

- 调查失败后，允许用户在原调查下发起新一轮尝试，无需另建调查。
- 新一轮尝试保留上一轮的失败原因和已有证据，不覆盖历史记录；上一轮失败仍是该轮的历史状态。
- 重试是新的调查尝试，不将上一轮失败改写为成功。

- 重试时允许调整被调查服务和日志时间范围；每轮尝试分别保留该轮的服务与时间范围，不覆盖历史范围。
- 上一轮已有证据可以保留，但不得自动视为覆盖了新一轮调整后的范围；新一轮的证据覆盖应按其实际调查范围判断。

- 首版调查失败后，仅由用户手动发起新一轮尝试，不自动重开新一轮。
- 单轮调查内对临时查询故障的重试不等于重开调查，不受上述手动发起规则限制；次数与间隔遵循“调查失败”中的查询重试规则。
- 用户手动重开不设累计次数上限，每轮均保留历史；启动仍须满足启动条件、旧轮已结束及并发限制。

当前骨架尚未实现多轮尝试、手动重开、逐轮范围保留与证据覆盖判断逻辑。

### 多轮调查的整体状态

- 调查列表中的整体状态跟随最新一轮调查尝试的状态。
- 例如，第一轮失败、第二轮正在排查时，整体显示“调查中”，历史中第一轮仍显示“失败”。
- 整体状态的变化不改写先前各轮的历史状态、失败原因或已有证据。

当前骨架尚未实现多轮状态展示逻辑。

### 已完成调查继续排查

- 已完成的调查允许在原调查下启动新一轮尝试，例如获得新证据后再次分析，无需另建调查。
- 上一轮保持“已完成”，其结论和历史记录保留，不因启动新一轮而被覆盖。
- 新一轮仍遵循调查启动条件、同一调查的并发限制及整体状态展示规则；新一轮进入“调查中”后，整体状态随之更新，上一轮状态不变。

当前骨架尚未实现已完成调查下启动新一轮及历史结论保留逻辑。

### 同一调查的并发限制

- 首版同一调查最多允许一轮尝试处于“调查中”，不允许多轮同时运行。
- 已有一轮正在排查时，重复点击启动或重试不得产生新的运行轮次。
- 同一调查的限制之外，整个实例同时最多允许 3 个调查运行；“正在停止”或“正在确认执行状态”的旧轮仍未结束，不能据此释放运行名额。
- 满额时直接提示稍后重试，不后台排队，也不创建貌似已运行的新轮次。

当前骨架尚未实现上述并发限制、满额提示及重复启动防护。

### 部分数据源不可用

- 部分数据源不可用时，如果其余来源仍能支持排查，允许继续调查，不因单一来源故障自动将调查标记为“失败”。
- 继续调查时必须明确标注缺失的数据源，以及证据覆盖不完整的情况。
- 数据源不可用导致的“查不到”不代表“没有异常”；不得据此排除相关故障原因。
- 结论仍遵守“证据不足时的结论表达”规则，继续调查不代表可以降低根因确认要求。

来源故障的查询超时、重试及无法继续时的失败判定遵循“调查失败”规则。当前骨架尚未实现来源故障处理和证据覆盖提示。

### 严重程度未评估时的展示

- 新调查尚未完成严重程度评估时，显示“未评估”，不默认归为“低”。
- “未评估”表示尚未作出严重程度判断，不代表低风险。

### 严重程度的业务含义

- 严重程度衡量故障对业务的影响，不表示排查优先级或根因判断的可信度。
- 根因尚不明确，不妨碍依据已知业务影响评估严重程度；例如核心业务不可用时，不能仅因原因不明而降低严重程度。
- 缺少业务影响评估依据时，仍遵循“未评估”的展示规则。

### 首版严重程度分级标准

- **高**：核心业务不可用，或大范围用户无法完成关键操作。
- **中**：部分业务受损、明显变慢，但仍能通过替代路径完成关键操作。
- **低**：影响局部且轻微，不妨碍关键业务操作。
- **未评估**：影响信息不足，无法判断。

以上为首版定性标准，不设首版统一量化阈值；评估依据尽量注明受影响的业务、用户范围、持续情况及替代路径，依据不足时为“未评估”。当前前端默认“低”的行为尚未按已确认规则调整。

### 严重程度的评估与调整

- Agent 根据业务影响证据给出严重程度评估，用户可以人工调整。
- 每次评估或调整都记录依据，并保留变更历史，不以新值覆盖历史记录。
- 业务影响信息不足时保持“未评估”，不强行给出高中低等级。

- 用户人工调整严重程度后，Agent 后续评估不得直接覆盖当前人工等级。
- Agent 可以给出新的等级建议及依据；只有用户确认后，才将建议应用为当前等级，并按上述规则保留变更历史。

- 新一轮启动不自动清空人工等级；保留等级不代表历史等级已验证当前影响，应展示评估时间。后续等级变更仍须人工确认，不由 Agent 覆盖。

当前骨架尚未实现严重程度评估、人工等级跨轮保留、评估时间展示、人工调整、建议确认及变更历史。

### 调查数据持久保存

- 首版持久保存调查记录、各轮尝试、脱敏证据、结论及变更历史，刷新页面或重启服务后仍可查看。
- 证据保存遵守已确认的脱敏规则；本节不授权保存未脱敏日志。
- 可重新查看已保存记录不等于运行中的调查能够在服务重启后自动续跑；运行中断后的处理见下节。

- 调查数据默认保留至最近一轮结束后 30 天；没有轮次的待处理记录自创建起算。
- 新一轮启动重新计算保留周期，运行中不清理；仅查看不延长保留期限。
- 到期前 7 天提示用户可延期；首版不静默自动永久删除，到期后标记为待用户确认清理，并明确清理范围及不可恢复性。

当前调查数据仅在前端内存中，持久保存、保留周期、延期提示及到期确认清理尚未实现。

### 服务中断后的调查处理

- 首版因服务重启而中断的调查不自动续跑。
- 执行失联时先显示“正在确认执行状态”，不直接将其视为已结束；必须确认旧执行不能继续运行或写入后，才将受影响轮次记为“失败”、允许新一轮，注明服务中断原因并保留已保存的证据。
- 单纯刷新页面不视为调查失败，不应因此终止仍在运行的调查。

- 页面断连本身也不视为执行终止或调查失败；“正在确认执行状态”期间仍为“调查中”，不得启动替代轮次。

当前骨架尚未实现运行中断识别、执行终止及写入停止的确认、“正在确认执行状态”展示和上述恢复处理；此处不指定具体确认机制。

### 调查列表的时间筛选

- 列表的“近 1 小时／近 24 小时”等时间范围按调查最后更新时间筛选，不按日志发生时间筛选。
- 日志时间范围属于各轮排查条件，应单独展示，与列表筛选时间区分。
- 时间以北京时间（UTC+8）展示，保存时使用统一时间基准；固定筛选区间左闭右开。
- 相对范围在应用筛选或刷新时计算；列表与概况同一次计算使用相同边界，翻页不改变该范围。

### 调查最后更新时间的更新规则

- 创建调查、启动新一轮、状态变化、新增证据、结论变化及严重程度调整时，更新调查最后更新时间。
- 仅查看、搜索或筛选不更新该时间。

当前前端尚未实现上述更新时间规则、统一时间展示与保存、筛选边界及相对范围计算，时间筛选也尚未实际生效。

### 顶部概况的统计范围

- 顶部概况指标与调查列表使用同一组搜索、服务和时间筛选条件。
- 统计范围为全部匹配记录，不限于当前页；翻页不改变统计范围。

- 首版概况只保留调查总数、活跃调查数、待处理调查数和证据总条数。
- 调查总数为匹配调查数；活跃调查数为匹配记录中整体状态为“调查中”的调查数；待处理调查数为整体状态为“待处理”的匹配调查数。
- 证据总条数为匹配调查最新轮证据条数之和；没有轮次的调查贡献为 0，不跨调查去重。
- 首版暂不展示待处理告警、证据完整率，不得用演示常量冒充真实统计。

当前前端概况尚未按上述指标及计算口径联动筛选，部分指标仍为演示常量，不代表已实现真实统计。

### 活跃调查的计算口径

- 在上述概况统计范围内，仅统计整体状态为“调查中”的调查，每个调查计一次，不累计历史轮次。
- “待处理”“已完成”“失败”“已取消”均不计入活跃调查。

当前前端已有按“调查中”计数的逻辑，但尚未接入多轮整体状态及统一筛选范围。

### 证据条数的计算口径

- 首版将调查列表中的“事件数”明确命名为“证据条数”，表示最新一轮调查尝试中已保存、去重后的证据记录数量。
- 不统计扫描到的全部日志，不累计历史轮次的证据条数；各历史轮次分别保留自己的证据条数。
- 证据条数不表示故障数量，也不表示已确认根因的数量。

当前前端仍使用“事件数”展示，尚未实现上述证据统计逻辑。

### 同一轮调查中的证据去重

- 同一轮调查中，重复获取同一来源的同一条原始日志，只保留一条证据记录，不重复计数。
- 不得仅凭日志文本相同就合并证据；内容相同但发生时间或来源不同的日志，可能是不同的原始记录。
- 无法可靠判断是否为同一条原始日志时，不自动合并。

- 判同优先使用来源标识与来源提供的稳定日志记录 ID；文件日志可使用稳定文件身份与偏移。
- 没有可靠 ID 时，不凭时间、文本摘要或脱敏后相同文本自动认定为同一条原始日志；无法可靠判同时保留记录，并提示可能重复。

当前骨架尚未实现上述原始日志判同、证据去重及可能重复提示逻辑。

## 技术栈

- 前端：Vue 3、TypeScript、Vite、Element Plus
- 后端：Python、FastAPI、Pydantic Settings、SQLAlchemy 2、Alembic
- 数据库：PostgreSQL 17

## 本地开发

### 1. 启动 PostgreSQL

```bash
docker compose up -d postgres
```

开发账号仅用于本机原型。部署或共享环境前请更换密码并通过环境变量注入凭据。

### 2. 启动 API

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# Git Bash: source .venv/Scripts/activate
pip install -r backend/requirements.txt
uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

API 健康检查：<http://127.0.0.1:8000/api/health>

交互式 API 文档：<http://127.0.0.1:8000/docs>

### 3. 启动前端

```bash
npm install
npm run dev
```

Vite 默认地址：<http://127.0.0.1:5173>。`/api` 请求会代理到本地 FastAPI。

## 当前骨架范围

前端包含调查工作台静态原型、搜索/服务筛选和本地新建调查交互；后端包含健康检查和 PostgreSQL 连接配置骨架。调查数据尚未接入 API，数据库迁移、日志连接器和 Agent 调查流程留待后续实现。
